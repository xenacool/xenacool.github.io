Bevy Composable Dragging Documentation

Introduction

Bevy Composable Dragging is a declarative dragging library for Bevy 0.20, ported from Dragology.

What It Solves

Instead of writing hand-crafted drop zones, hit tests, and drag state machines, you describe your interface as a pure function from state to a View, and attach a drag spec to every node that can be dragged. The engine renders the target states speculatively, finds the dragged node by id in each of them, and synthesizes the preview while dragging and the new state on release.

A single draggable circle toggling between two states. Run cargo run --example hello --features pbr to reproduce it.

Key Concepts

  • Views: Plain-data descriptions of scenes — flat lists of nodes with geometry, transforms, colors, and optional drag specs
  • Operators: Declarative drag behaviors (between, closest, vary, etc.) that compile into per-frame behavior
  • Drag Spaces: Planes, axes, and screen-facing planes that resolve pointer rays to world points
  • Blending: Smooth interpolation between views, with presence animations for emerging and disappearing nodes
  • Gizmos: Transform handles (translate, rotate, scale) built from ordinary draggable nodes
  • Editor Tools: Heightmaps, curve handles, HUDs, and radial menus for building complete editors

Design Philosophy

Bevy Composable Dragging follows these principles:

  1. Declarative: Describe what a drag does, not how it works frame by frame
  2. Composable: Specs are plain data that combine freely — no state machines or enums
  3. Pure views: The view function is pure; state holds everything, including HUD screen size
  4. Bevy-native: Outputs standard Mesh, Transform, and StandardMaterial types
  5. Feature-gated: The core library needs only bevy_color; PBR and gradient features are optional

Getting Started

Installation

Add bevy_composable_dragging to your Cargo.toml:

[dependencies]
bevy = "0.20"
bevy_composable_dragging = { version = "0.3", features = ["pbr"] }

The pbr feature enables 3D scenes with PBR materials and mesh picking. For gradient shapes, add shapes-3d or shapes-2d:

bevy_composable_dragging = { version = "0.3", features = ["shapes-3d"] }

Your First Draggable Interface

use bevy::prelude::*;
use bevy_composable_dragging::ops::between;
use bevy_composable_dragging::{DraggablePlugin, View, ViewNode};

fn view(on: &bool) -> View<bool> {
    let x = if *on { 1.0 } else { -1.0 };
    View::new().with(
        ViewNode::circle("knob", 1.0)
            .at_xy(Vec2::new(x, 0.0))
            .draggable(|| between([false, true])),
    )
}

fn main() {
    App::new()
        .add_plugins(DefaultPlugins)
        .add_plugins(DraggablePlugin::new(false, view))
        .run();
}

This creates a circle that toggles between x = -1 and x = 1. Dragging it smoothly animates between the two states, and releasing commits the nearest one.

Understanding the API

The core API has three main types:

  1. View<S> — A flat list of ViewNodes describing your scene. Build it as a pure function of your state type S.
  2. ViewNode<S> — A single element with an id, geometry, transform, color, and optional drag spec.
  3. DragSpec<S> — A declarative description of how a node can be dragged, built with operators from the ops module.

State and View Functions

Your state type S holds everything your interface needs. The view function fn(&S) -> View<S> must be pure — no side effects, no external state. The engine calls it many times per frame with speculative states to compute drag previews.

#![allow(unused)]
fn main() {
#[derive(Clone)]
struct Slider {
    value: f32,
}

fn view(state: &Slider) -> View<Slider> {
    View::new()
        .with(ViewNode::circle("handle", 0.3).at_xy(Vec2::new(state.value, 0.0)))
}
}

Views and Nodes

A View<S> is a flat list of ViewNodes, each identified by a NodeId (a string). Nothing in a view touches the ECS — it is plain data that the engine evaluates cheaply for many speculative states.

Building a View

#![allow(unused)]
fn main() {
use bevy_composable_dragging::{View, ViewNode};

fn view(state: &MyState) -> View<MyState> {
    View::new()
        .with(ViewNode::circle("a", 0.5).at_xy(Vec2::new(-1.0, 0.0)))
        .with(ViewNode::circle("b", 0.5).at_xy(Vec2::new(1.0, 0.0)))
}
}

Transforms and Hierarchy

Nodes support full 3D transforms and parent-child hierarchy. A child node is positioned relative to its parent using .with_parent():

#![allow(unused)]
fn main() {
View::new()
    .with(ViewNode::sphere("parent", 1.0).at(Vec3::new(0.0, 2.0, 0.0)))
    .with(ViewNode::sphere("child", 0.3)
        .with_parent("parent")
        .at(Vec3::new(1.5, 0.0, 0.0)))
}

Transform methods:

  • at(Vec3) — full 3D position
  • at_xy(Vec2) — 2D shorthand
  • with_rotation(Quat) — full rotation
  • with_rotation_xy(f32) — Z-axis rotation in radians
  • scaled(Vec3) — full scale
  • scaled_xy(Vec2) — uniform 2D scale

Colors and Styles

#![allow(unused)]
fn main() {
ViewNode::sphere("colored", 1.0)
    .with_color(Color::srgb(0.9, 0.3, 0.2))
}

With the gradmesh feature, nodes can carry a Style for gradient shading:

#![allow(unused)]
fn main() {
use bevy_gradmesh::Style;

ViewNode::sphere("gradient", 1.0)
    .with_style(Style::dual_directional([0.3, 0.2, 0.1], [0.9, 0.7, 0.5], [0.0, 1.0, 0.0]))
}

Presence and Opacity

Control how nodes appear and disappear during blends:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::Presence;

ViewNode::sphere("fade", 1.0)
    .presence(Presence::Fade)            // fades in/out during blends
    .with_opacity(0.8)                   // semi-transparent
}

Presence options:

  • Presence::Fade — node fades in and out
  • Presence::Emerge — node emerges from the dragged node
  • Presence::Pop — node appears instantly

Rendering Modes

#![allow(unused)]
fn main() {
// 3D spatial rendering (default)
ViewNode::sphere("spatial", 1.0).spatial()

// 2D flat rendering (requires gradmesh)
ViewNode::sphere("flat", 1.0).flat()
}

ViewNode::spatial() draws a node as a Mesh3d for a Camera3d, and ViewNode::flat() draws it as a Mesh2d for a Camera2d, overriding the plugin default. Together with .on_layer(), they build a HUD from ordinary nodes over a 3D scene: give the HUD nodes .flat().on_layer(HUD) and add a Camera2d with that layer and a higher order next to the scene camera. Each camera only draws the nodes on its own layers, and a press from it only picks those nodes, so the HUD and the scene never take presses from each other.

Layers

Nodes live on render layers for picking and rendering isolation:

#![allow(unused)]
fn main() {
ViewNode::sphere("hud", 1.0).on_layer(2)
}

Gizmo handles use layer 31 (GIZMO_LAYER) so they are always picked first.

Operators

Operators build DragSpecs declaratively. They follow Figure 4 of the Dragology paper and compose freely — specs are plain data that compile into per-frame behavior.

state — Switch to a Fixed State

The simplest operator: dragging switches to the given state.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::state;

ViewNode::circle("button", 0.3)
    .draggable(|| state(true))
}

between — Toggle Between States

Drag between a list of discrete states. The preview interpolates between them, and the nearest state wins on release.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::between;

ViewNode::circle("knob", 0.5)
    .draggable(|| between([false, true]))
}

With custom interpolation and drop rules:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::{between_with, BetweenOptions, Interpolation};

between_with([a, b, c, d], BetweenOptions::new()
    .with_interpolation(Interpolation::NaturalNeighbor)
)

*Three states arranged in a triangle. Run `cargo run --example three_way --features pbr`.*

# `closest` — Pick the Nearest State

Evaluate many drag specs and pick the one whose dragged node is closest to the pointer.

```rust
use bevy_composable_dragging::ops::closest_states;

ViewNode::circle("item", 0.3)
    .draggable(|| closest_states((0..10).map(|i| {
        let mut s = state.clone();
        s.positions[i] = i as f32;
        s
    })))
}

Drag items to reorder a list. Run cargo run --example reorder_list --features pbr.

vary — Continuously Change a Value

Continuously change a numeric parameter of your state as you drag.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::vary;
use bevy_composable_dragging::param;

ViewNode::circle("handle", 0.3)
    .draggable(|| vary(state.clone(), [param!(Slider, value)]))
}

With range constraints, use vary_constrained:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::vary_constrained;
use bevy_composable_dragging::{param, constraint};

vary_constrained(
    state.clone(),
    [param!(Slider, value)],
    constraint::in_range(param!(Slider, value), 0.0, 10.0),
)
}

A continuous slider. Run cargo run --example slider --features pbr.

substate — Delegate to a Nested State

Apply an operator to a field of your state, using a Lens:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::{substate, between, Lens};

let lens = Lens::new(
    |s: &MyState| s.inner.clone(),
    |s: &MyState, inner| MyState { inner, ..s.clone() },
);

ViewNode::circle("nested", 0.3)
    .draggable(|| substate(lens.clone(), between([0, 1, 2])))
}

drop_target — Define a Drop Zone

Mark a node as a drop target that accepts drops from other nodes.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::drop_target;

ViewNode::rectangle("zone", Vec2::splat(2.0))
    .draggable(|| drop_target("dropper", dropped_state))
}

react_to — React to External Values

Rebuild the drag spec when an external value changes, such as a modifier key:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::react_to;

ViewNode::circle("reactor", 0.3)
    .draggable(|| react_to(
        || shift_held.load(std::sync::atomic::Ordering::Relaxed),
        |shift| if *shift { /* spec with shift */ } else { /* normal spec */ },
    ))
}

button — Click Without Dragging

A node that activates on press-and-release without moving:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::button;

ViewNode::circle("btn", 0.3)
    .draggable(|| button(clicked_state, 0.1))
}

custom — Full Control

Provide a custom compile function for complete control over drag behavior.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::custom;

ViewNode::circle("custom", 0.3)
    .draggable(|| custom(|context| {
        // Build a DragBehavior from scratch
        // ...
    }))
}

Value Operators

Three operators for direct value editing along axes and planes:

  • along_axis — Change a value by dragging along a line
  • around_axis — Change a value by dragging around a ring (rotation)
  • across_plane — Change a value by dragging across a plane

These are used by gizmos and curve handles for precise editing with snapping.

Spec Modifiers

Every DragSpec supports modifier methods:

ModifierPurpose
.with_floating()Lift the node along the space normal while dragging
.when_far(background, gap)Switch to background spec when pointer is far
.with_snap_radius(radius)Snap to the target within this radius
.on_drop(state)Override the drop state
.with_chaining()Continue dragging in the new state

.with_init_context(fn)Modify the drag context at start

Chaining

.with_chaining() lets a drag continue seamlessly after switching states:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::closest_states;

ViewNode::circle("item", 0.3)
    .draggable(|| closest_states(states).with_chaining())
}

Drag Spaces

A drag space resolves the pointer ray to a world point. Operators then work on world positions and node transforms, so drags on the ground, along an axis, and on a transform gizmo share one code path.

Types of Drag Spaces

Plane

The default space: a plane with any origin and normal.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::DragSpace;
use bevy::math::{Dir3, Vec3};

// XY plane at z = 0 (default)
DragSpace::world_plane(0.0)

// Ground plane at y = 0
DragSpace::plane(Vec3::ZERO, Dir3::Y)
}

Axis

Drag along a line. The pointer position is the nearest point on the line to the pointer ray.

#![allow(unused)]
fn main() {
// Drag along the Y axis
DragSpace::axis(Vec3::ZERO, Dir3::Y)
}

Screen

A plane through the dragged node that faces the camera, fixed when the drag starts.

#![allow(unused)]
fn main() {
DragSpace::screen()
}

Setting a Drag Space

#![allow(unused)]
fn main() {
use bevy_composable_dragging::{DragSpace, ViewNode};
use bevy::math::{Dir3, Vec3};

// Default: drags in the XY plane
ViewNode::sphere("default", 1.0)
    .draggable(|| /* spec */)

// Custom: drag on the ground
ViewNode::sphere("ground", 1.0)
    .draggable_in(
        DragSpace::plane(Vec3::ZERO, Dir3::Y),
        || /* spec */,
    )
}

How Spaces Work

When you press a node, the engine resolves the pointer ray against the node’s drag space:

  1. Plane: intersect the ray with the plane
  2. Axis: find the nearest point on the axis line to the ray
  3. Screen: create a plane through the node facing the camera, then intersect

Operators like closest, between, and with_floating work unchanged in any space. Gaps are measured after projecting positions onto the space, and 2D weights use the local basis of the space.

Picking

A press picks the node whose oriented bounds the pointer ray hits first (View::hit_test), then grabs its nearest draggable ancestor. Nodes on higher render layers are picked first — gizmo handles use layer 31 so they are always picked above scene geometry.

Blending

The engine blends views to produce smooth animations. Every animatable property of a ViewNode implements the Blend trait, and lerp_views interpolates between two views by node id.

How Blending Works

When a drag starts, the engine evaluates the view function for the current state and each target state. As the pointer moves, it blends between the start view and the target view, producing a smooth preview. On release, the state switches and the view animates to the new target.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::lerp_views;

let preview = lerp_views(&start_view, &target_view, t);
}

Presence

When a node exists in one view but not the other, its Presence determines how it appears or disappears:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::Presence;

// Fade in/out with opacity
Presence::Fade

// Emerge from the dragged node's position
Presence::Emerge

// Appear instantly
Presence::Pop
}

View Blending Functions

#![allow(unused)]
fn main() {
use bevy_composable_dragging::{lerp_views, blend_views, lerp_transform};

// Linear interpolation between two views
let blended = lerp_views(&a, &b, 0.5);

// Natural neighbor blending (for multiple views)
let blended = blend_views(&[&a, &b, &c], &[0.5, 0.3, 0.2]);

// Interpolate a single transform
let t = lerp_transform(&t1, &t2, 0.5);
}

Overshoot

ViewNode::with_overshoot makes a node’s transform run past its target by a fraction of the distance and settle back, creating a spring-like animation:

#![allow(unused)]
fn main() {
ViewNode::sphere("bouncy", 1.0)
    .with_overshoot(0.12)  // 12% overshoot
}

The HUD uses 12% overshoot for all its elements.

Geometry Morphing

When two views use different geometries for the same node, the engine morphs between them. With bevy_gradmesh, shapes are quantized to 32 morph steps, bounding the number of distinct meshes.

Natural neighbor blending across four control points. Run cargo run --example blend_square --features pbr.

Gizmos

The gizmo module (behind the gradmesh feature) adds translate, rotate, and scale handles around a node as ordinary draggable nodes. Each handle uses value operators (along_axis, around_axis, across_plane) with snapping.

Adding a Gizmo

#![allow(unused)]
fn main() {
use bevy::prelude::Transform;
use bevy_composable_dragging::gizmo::Gizmo;
use bevy_composable_dragging::ops::Snap;
use bevy_composable_dragging::{View, ViewNode};

fn view(state: &MyState) -> View<MyState> {
    let mut view = View::new();
    view.push(ViewNode::sphere("object", 1.0).at(state.position));
    
    let transform = Transform::from_translation(state.position);
    Gizmo::new("object", transform)
        .translate(Snap::step(0.1), |s, offset| {
            let mut s = s.clone();
            s.position += offset;
            s
        })
        .rotate(Snap::step(0.1), |s, rotation| {
            let mut s = s.clone();
            s.rotation *= rotation;
            s
        })
        .scale_uniform(Snap::step(0.1), |s, scale| {
            let mut s = s.clone();
            s.scale *= scale;
            s
        })
        .add_to(&mut view);
    view
}
}

Snapping

Every handle accepts a Snap that pulls the preview onto discrete steps:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::ops::Snap;

// No snapping — continuous values
Snap::NONE

// Snap to multiples of 0.1
Snap::step(0.1)

// Snap to multiples with an offset
Snap::step_with_offset(0.1, 0.05)
}

Revealing Gizmos

An editor typically shows the gizmo only for the selected object and only when the active tool transforms it. Implement GizmoReveal on your state:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::gizmo::GizmoReveal;

#[derive(Clone)]
struct Editor {
    selected: Option<String>,
    tool: Tool,
}

impl GizmoReveal for Editor {
    fn reveals_gizmo(&self) -> bool {
        self.selected.is_some() && self.tool == Tool::Transform
    }
}
}

Then use Gizmo::add_if_revealed instead of add_to:

#![allow(unused)]
fn main() {
Gizmo::new("object", transform)
    .translate(Snap::step(0.1), |s, offset| {
        let mut s = s.clone();
        s.position += offset;
        s
    })
    .add_if_revealed(&mut view, &state);
}

Render Layer

Gizmo handles live on render layer 31 (GIZMO_LAYER) so they are always picked first, even when scene geometry covers them.

Camera Helpers

The example helpers in examples/common include the gizmo layer automatically:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::examples::common::spawn_perspective_scene;

    spawn_perspective_scene(&mut commands, Vec3::new(5.0, 5.0, 5.0), Vec3::ZERO);
}
}

Footprint

Gizmo::footprint returns the world positions of all handle centers, useful for HUD layout to keep elements clear of the gizmo.

Curve Handles

The handles module (behind the gradmesh feature) provides CurveHandles for editing 3D curves with draggable control points, width handles, and roll rings.

Adding Curve Handles

#![allow(unused)]
fn main() {
use bevy_composable_dragging::handles::{CurveHandles, Lateral};
use bevy_composable_dragging::ops::Snap;
use bevy_composable_dragging::{View, ViewNode};

#[derive(Clone)]
struct Road {
    points: Vec<Vec3>,
    half_widths: Vec<f32>,
    selected: Option<usize>,
}

fn view(road: &Road) -> View<Road> {
    let mut view = View::new();
    view.push(ViewNode::cuboid("road", Vec3::new(1.0, 0.1, 8.0), 0.0));
    
    let lateral: Vec<Lateral> = road.half_widths.iter()
        .map(|hw| Lateral { right: Vec3::X, half_width: *hw })
        .collect();
    
    CurveHandles::new("road", Transform::IDENTITY, &road.points)
        .selected(road.selected)
        .move_point(Snap::step(0.1), |road, index, offset| {
            let mut road = road.clone();
            road.points[index] += offset;
            road.selected = Some(index);
            road
        })
        .width(&lateral, Snap::step(0.1), |road, index, change| {
            let mut road = road.clone();
            road.half_widths[index] += change;
            road
        })
        .add_to(&mut view);
    view
}
}

Handle Types

HandleShapeFunction
Control pointGem (sphere)Move point across the ground plane
RaiseCone above gemRaise or lower the point
InsertSmall gem between pointsInsert a new control point
WidthCube (selected point)Adjust road width at this point
RollTorus ring (selected point)Rotate the cross-section at this point

Configuration

#![allow(unused)]
fn main() {
CurveHandles::new("road", transform, &points)
    // Show selected point's extra handles
    .selected(Some(0))
    
    // Move points across the ground
    .move_point(Snap::step(0.1), move_fn)
    
    // Raise/lower points
    .raise_point(Snap::step(0.1), raise_fn)
    
    // Insert new points between existing ones
    .insert_point(insert_fn)
    
    // Adjust width at selected point
    .width(&lateral, Snap::step(0.1), width_fn)
    
    // Roll cross-section at selected point
    .roll(Snap::step(0.05), roll_fn)
}

Closures

Each handle takes a closure that receives the original state, the point index, and the measured value, and returns the new state. Pressing a handle also selects its point, so the closure can use this for selection.

Footprint

CurveHandles::footprint(index) returns the 2D bounds of the handles for a specific control point, useful for HUD layout to avoid overlapping elements.

Heightmaps

The heightmap module provides an editable terrain grid that a brush raises, lowers, and cuts holes in. It needs no rendering feature — the heightmap is plain data, and a renderer builds meshes from the chunks it marks as dirty.

Creating a Heightmap

#![allow(unused)]
fn main() {
use bevy::math::{UVec2, Vec2};
use bevy_composable_dragging::heightmap::{Brush, Grid, Heightmap};

// 4x4 chunks, 16 vertices per side, 0.5 unit spacing
let grid = Grid::new(UVec2::new(4, 4), 16, Vec2::ZERO, 0.5);

// Flat terrain at height 0, range -1 to 3
let terrain = Heightmap::new(grid, 0.0, -1.0, 3.0);
}

Editing with a Brush

#![allow(unused)]
fn main() {
let edited = terrain.raised(&Brush {
    center: Vec2::new(4.0, 4.0),  // brush position on the ground
    radius: 2.0,                   // how far it reaches
    amount: 1.0,                   // positive raises, negative lowers
    falloff: 1.0,                  // 1.0 = smooth, 0.0 = hard edge
});
}

Reading the Terrain

#![allow(unused)]
fn main() {
// Height at a point (including over holes)
let height = terrain.surface(Vec2::new(4.0, 4.0));

// Height only where the ground exists (None over holes)
let height = terrain.height_at(Vec2::new(4.0, 4.0));

// Surface normal for lighting or collision
let normal = terrain.normal_at(Vec2::new(4.0, 4.0));

// Ray intersection for picking
if let Some(hit) = terrain.hit(ray) {
    println!("Hit at {}", hit);
}
}

Chunks and Dirty Tracking

The grid is divided into chunks. Copying a heightmap is cheap — only the edited chunks are copied. Each chunk has a key that changes when its heights or holes change:

#![allow(unused)]
fn main() {
// Check every chunk for changes
for chunk in 0..terrain.chunk_count() {
    let key = terrain.chunk_key(chunk);
    if key != previous_keys[chunk] {
        // Rebuild the mesh for this chunk
        let heights = terrain.chunk_heights(chunk);
        let holes = terrain.chunk_holes(chunk);
    }
}
}

Holes

Cut holes in the terrain without losing the height data underneath. Holes are a mask over the cells, so filling a hole restores the original height:

#![allow(unused)]
fn main() {
// Cut a hole
let with_hole = terrain.with_holes(Vec2::new(2.0, 2.0), 1.0, true);

// Fill it back — the original height returns
let filled = with_hole.with_holes(Vec2::new(2.0, 2.0), 1.0, false);
}

HUDs

The hud module (behind the gradmesh feature) provides a heads-up display built from ordinary nodes. Elements are rounded signed distance fields — fills and borders drawn per pixel so edges stay crisp at any size.

Screen and Layout

The Screen holds the HUD size and the projection of the scene camera. The Layout computes where corner anchors and radial menu petals go from the screen size.

#![allow(unused)]
fn main() {
use bevy_composable_dragging::hud::{HudHost, HudPlugin, HudProjectionCamera, Screen};

#[derive(Clone)]
struct Editor {
    screen: Screen,
}

impl HudHost for Editor {
    fn screen(&self) -> &Screen {
        &self.screen
    }

    fn with_screen(&self, screen: Screen) -> Self {
        Self { screen }
    }
}
}

Register HudPlugin to keep the screen in sync with the window:

#![allow(unused)]
fn main() {
App::new()
    .add_plugins(DefaultPlugins)
    .add_plugins(DraggablePlugin::new(Editor { screen: Screen::default() }, view))
    .add_plugins(HudPlugin::<Editor>::new(720.0))
    .add_systems(Startup, |mut commands: Commands| {
        commands.spawn((Camera3d::default(), HudProjectionCamera));
    })
    .run();
}

Theme

A Theme holds colors, border width, tween settings, and the render layer. The HUD builders are methods of the theme:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::hud::{Layout, Theme};

let theme = Theme::default();
let layout = Layout::new(state.screen());

// Build a bordered panel (returns 2 nodes: plate + border)
let panel = theme.panel("panel", Vec2::new(200.0, 100.0), Vec2::ZERO, &layout);

// Build a filled disc
let disc = theme.disc("action", 20.0, theme.fill, Vec3::ZERO);
}

Radial Menus

The radial module (behind the gradmesh feature) builds a radial menu on the HUD: a hub, rings of petals, and a status panel. Every petal is an ordinary node that blooms out of the hub when its ring opens.

Traits

Three traits connect your types to the menu:

Petal

Defines what a menu item looks like and does:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::radial::Petal;
use bevy_gradmesh::Shape;

#[derive(Clone, Copy, PartialEq, Debug)]
enum Tool { Pen, Eraser }

impl Petal<MyState> for Tool {
    fn name(&self) -> String {
        format!("{self:?}")
    }

    fn label(&self, _state: &MyState) -> String {
        self.name()
    }

    fn accent(&self) -> Color {
        Color::srgb(0.24, 0.42, 0.8)
    }

    fn glyph(&self) -> Shape {
        // Return a small shape for the petal icon
        Shape::circle(0.5)
    }

    fn is_active(&self, state: &MyState) -> bool {
        state.tool == *self
    }

    fn press(&self, state: &MyState) -> MyState {
        let mut s = state.clone();
        s.tool = *self;
        s.menu = None;
        s
    }
}
}

Ring

Defines a ring of items:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::radial::Ring;

#[derive(Clone, Copy, PartialEq, Debug)]
enum Page { Tools }

impl Ring<MyState> for Page {
    type Item = Tool;

    fn name(&self) -> String {
        "tools".into()
    }

    fn items(&self, _state: &MyState) -> Vec<Tool> {
        vec![Tool::Pen, Tool::Eraser]
    }

    fn all(_state: &MyState) -> Vec<Self> {
        vec![Page::Tools]
    }
}
}

RadialHost

Connects the state to the menu. It extends HudHost:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::radial::RadialHost;
use bevy_composable_dragging::hud::Layout;

impl RadialHost for MyState {
    type Ring = Page;

    fn root(&self) -> Page {
        Page::Tools
    }

    fn menu(&self) -> Option<Page> {
        self.menu.clone()
    }

    fn with_menu(&self, menu: Option<Page>) -> Self {
        Self { menu, ..self.clone() }
    }

    fn pop_center(&self, layout: &Layout) -> Vec2 {
        layout.home()
    }

    fn status(&self) -> String {
        format!("Tool: {:?}", self.tool)
    }
}
}

Adding the Menu

push_menu builds the menu nodes; call it from your view function with the layout and theme:

#![allow(unused)]

    let mut view = View::new();
    // ... scene nodes ...
    let layout = Layout::new(state.screen());
    let theme = /* your theme */;
    push_menu(&mut view, &state_arc, &layout, &theme);
    view
}

// Register the plugin for text labels

}

App Content

A view is plain data, but the entity of a node that is on screen is an ordinary Bevy entity, and an app often wants more on it than the engine knows about: a marker component, an observer for Pointer<Click>, a sound that plays when it is added. ViewNode::with_scene attaches a Bevy scene to a node for exactly that.

ViewNode::sphere("door", 0.5).with_scene(|| {
    bsn! {
        Door
        on(|event: On<Pointer<Click>>, mut commands: Commands| {
            commands.trigger(DoorClicked(event.entity));
        })
    }
})

The contract

  • The view stays pure. view(&S) never reads or writes the world. The function you pass to with_scene is only data until the engine calls it, and the engine calls it only for a node that is shown.
  • Previews never build content. While a drag evaluates states that are never shown, the engine reads the plain data of the nodes and calls no scene function. App components, hooks and observers therefore never run for a preview. To react to a preview, use react_to, during or on_drop.
  • The engine owns what it writes. That is the name, the transform, the mesh, the material, the render layers, the picking and the visibility of the entity. The engine writes them after the scene, so the scene cannot change them.
  • The app owns the rest. The scene is applied once, when the node first appears, and the engine never touches what it added again. Applying a scene twice would reset the state of the app, which is why it is applied once.
  • A node keeps its entity for as long as its id is in the view, so components and observers survive every change of state. A node that disappears is despawned after its presence animation.
  • No children. The engine owns the hierarchy of the nodes, so a scene must not describe children.
  • No opt-out. There is no way for a view function to touch the world and no mode that builds content for previews.

A node that first appears while one view blends into another takes its scene from the view the blend settles on.

View functions are Clone

The engine keeps one copy of the view function for the model and one for each drag, and never shares them. A closure that captures only Copy or Clone data, as most do, is Clone already. A view function that captures something that is not, such as a Box<dyn Fn>, needs that captured value to be wrapped in something that is.

Custom Operators

Build a custom operator by returning a DragSpec from a function:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::{DragSpec, DragBehavior, DragContext};
use bevy_composable_dragging::behavior::Frame;

fn my_operator<S: Clone>(states: impl IntoIterator<Item = S>) -> DragSpec<S> {
    DragSpec::new(move |context: &DragContext<S>| {
        // Build a DragBehavior that produces Frame values
        // Each frame has a view, drop_state, and gap
        DragBehavior::new(/* ... */)
    })
}
}

Parameters and Constraints

The param! macro builds getter/setter pairs for f32 fields:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::{param, Param};
use bevy_composable_dragging::constraint;

struct Meeting { start: f32 }
struct Schedule { meetings: Vec<Meeting> }

let second_start = param!(Schedule, meetings[1].start);

// Constrain a parameter to a range
let bounded = constraint::in_range(
    param!(Schedule, meetings[0].start),
    0.0, 24.0,
);
}

Combine constraints:

#![allow(unused)]
fn main() {
use bevy_composable_dragging::constraint::{and, less_than, at_least};

let ordered = and([
    at_least(param!(State, x), 0.0),
    less_than(param!(State, x), param!(State, y)),
]);
}

Set parameter scale for faster solver convergence:

#![allow(unused)]
fn main() {
let scaled = param!(State, pixel_x).with_scale(100.0);
}

Chaining Drags

.with_chaining() continues a drag after switching states:

#![allow(unused)]

ViewNode::circle("item", 0.3).draggable(|| {
    closest_states(states).with_chaining()

The Chaining struct controls which node and spec continue the drag:

#![allow(unused)]

    .following(new_spec)
    .with_transition(0.2)

Physics Integration

Combine dragging with physics engines like avian3d. The physics_lab example demonstrates dragging shapes onto a grid, simulating them with rigid bodies, and grabbing bodies during simulation.

Performance

  • Views are plain data — no ECS overhead for speculative evaluation
  • Geometry morphing is quantized to 32 steps
  • A heightmap is two flat buffers, so a copy is two memory copies and an edit names only the chunks it reaches
  • Gizmo handles use a dedicated render layer for fast picking

Differences from Dragology

The port aims to be faithful to the operators and behavior of Dragology. These differences are deliberate:

  • Solver. Dragology minimizes with COBYLA. The only COBYLA crate for Rust declares no license, so vary uses a Nelder–Mead search with a penalty stage instead (src/solver.rs). It reproduces the cases of Dragology’s optimization.test.ts that are ported into the unit tests, including equality lines and a pin on a fixed distance from a point. It is meant for the one to three parameters that drags vary; with many parameters or hard curved constraints COBYLA may do better.
  • between drop rule. Dragology drops onto the target nearest the pointer. The default here drops onto the target with the largest blend weight; DropRule::NearestTarget selects Dragology’s rule.
  • drop_target bounds. The default measures the target in the state the drag started from, so it keeps working when a drop removes the target. Dragology measures it in the target state; drop_target_with_bounds does that.
  • with_overlay. The overlay is a list of ordinary non-draggable nodes, in the overlay- namespace, instead of SVG. There is no tree view or overlay visualization of operators.
  • with_chaining and the chaining of with_snap_radius_options need a state that can be compared with PartialEq, because Dragology compares drop and start state with deep equality.
  • substate previews of the sub-spec are not draggable, because a drag factory of the part cannot be turned into one of the whole.
  • tactile_tessellations. A new tile starts at its palette item instead of the canvas origin, the dragged tile is raised by the spec instead of through a z-index from the dragged id, the center of the tile follows the pointer by resetting the grab offset (Dragology’s withInitContext({ anchorPos })), and the outline of a polygon is a larger polygon behind it. Snap candidates, the overlap test, rotation along the shortest arc, when_far and the trash bin behave as in the original.
  • 3D drag spaces and gizmos are additions. Dragology drags in the plane of the page. Here a drag resolves the pointer in a DragSpace (plane, axis or camera-facing plane), operators work on world positions and Transforms, nodes are picked by oriented bounds, and the value operators and Gizmo build on that. Geometry::Grad takes any bevy_gradmesh shape where Dragology draws SVG elements; text, filters and drop shadows have no counterpart.
  • Blending of different point counts. Dragology morphs paths with different segment counts; bevy_gradmesh 0.3 resamples polygons of different lengths in Shape::lerp, so tiles that change their number of sides morph here too. Shapes of different kinds still come from the nearer state.
  • Not ported: the SVG and React layer, the tree and path utilities, the studio and benchmark pages, amb (a helper of the demos), and the studio demos nodes and noodles, sticky notes, twisted trees, animate algebra and the spec designer.

The test cases of Dragology’s closest.test.tsx, userOps.test.tsx, math/delaunay.test.ts, math/natural-neighbor.test.ts and math/optimization.test.ts are ported into the unit tests of closest, custom, weights and the solver.

Migrating from 0.2 to 0.3

Version 0.3 removes the last shared ownership from the library. Three things change for code that uses it, and one thing is new.

View functions must be Clone

ViewFn<S> was an Arc<dyn Fn(&S) -> View<S>>. It is now a struct that owns a boxed closure and clones whatever the closure captures, so the model, the plugin and every drag each hold their own copy instead of sharing one.

  • DraggablePlugin::new, DragModel::new and DragContext::new take impl Fn(&S) -> View<S> + Clone + Send + Sync + 'static. A closure that captures nothing, or only Copy and Clone data, already is Clone, so most code compiles unchanged.
  • A closure that captures something that is not Clone needs it wrapped in something that is, or the data needs to move into the state S, where a view function belongs anyway.
  • Code that built an Arc to pass as a ViewFn passes the closure itself. Code that called a ViewFn as a function calls ViewFn::call. DragContext::with_view_fn takes a ViewFn that is already built.

Heightmaps are flat buffers

Heightmap no longer shares chunks through Arc. It keeps the heights and the holes of the whole map in two flat buffers laid out chunk by chunk, so copying one is two memory copies and an edit still reports the chunks it reaches through chunk_key and chunk_heights. The public methods are unchanged; only code that relied on a copy being a few pointer clones notices.

The bevy_scene feature

The crate now depends on Bevy’s bevy_scene feature, and DraggablePlugin adds ScenePlugin when the app has none.

New: scenes on nodes

ViewNode::with_scene gives a node components and observers of the app’s own. The scene is built only when the node first appears, never for the previews of a drag. See App Content for the contract.
